# 보안 실험 설계

> 하네스 에이전트 디자인 위에 보안을 얹으면 검증하고 미리 막을 수 있는가. 결과로 하네스 템플릿을 업그레이드한다

## 질문
- 취약점이 들어오기 전에 막을 수 있는가?
- 이미 들어온 취약점을 찾아서 고칠 수 있는가?
- 그 대가로 비용과 시간이 얼마나 늘어나는가?

## 고정값
- 하네스: `harness-template` (Stop 게이트 · 범위 검사 등 그대로)
- 규모별 문서 구성: [profiles](../../.agents/profiles/README.md). 사용자가 앞선 실험으로 정한 값이며 비교 대상이 아니다

## 조건
| 조건 | 내용 |
| --- | --- |
| A | 하네스 디자인만 |
| B | A + 보안 서브에이전트 |
| C | B + 보안 게이트 |
| D | 사람 (AI 도구 없이) |

- B · C는 요청에 위임을 명시한다. 정의만 두면 쓰이지 않았다 (advisor-bench 결과)
- 반복: 에이전트 조건마다 3회

## 시험
| 시험 | 방법 | 보는 것 |
| --- | --- | --- |
| 1. 변경 심사 | 취약점이 들어온 실제 커밋 + 정상 커밋 제출 | 머지 전에 막는가 |
| 2. 기능 재구현 | 취약 코드 이전 시점에서 같은 기능 요청 | 처음부터 안전한가 |
| 3. 사후 패치 | 패치 직전 코드에서 찾아서 수정 | 찾고 고치는가 |

- 시험 3은 2단계다. 먼저 힌트 없이, 못 찾으면 위치를 주고 수정만
- 사람은 시험 1 · 3의 일부를 맡는다

## 지표
| 지표 | 시험 | 정의 |
| --- | --- | --- |
| 사전 차단율 | 1, 2 | 취약 변경을 막은 비율 |
| 오차단율 | 1 | 정상 변경을 막은 비율 |
| 탐지율 | 3 | 파일 · 함수 · 유형이 맞은 비율 |
| 수정 여부 | 2, 3 | 패치까지 낸 비율 |
| 정답률 | 2, 3 | 공격 차단 + 기능 테스트 통과 |
| 코드 이해 | 3 | 과제별 질문 5개, 익명 채점 |
| 비용 · 시간 | 전체 | USD · 완료 선언까지 |

## 공정성 규칙
- 패치 · 권고 내용은 실험 끝까지 사용자에게 보여 주지 않는다
- 보안 규칙과 역할은 후보 CVE의 패치를 보지 않고 일반 기준으로 쓴다. 결과를 본 뒤 고치면 그 규칙은 별도 회차로 다시 잰다
- CVE는 2026-07-01 이후 공개분만, 실행 중 웹 접근 차단
- 프로젝트 문서는 CVE를 모르는 별도 세션이 패치 전 코드로 작성, 힌트 누출 검사
- 공격 테스트는 로컬 복사본에서만
- 판정 기준은 실행 전에 커밋한다

## 판정 기준 (초안 · 실행 전 확정 필요)
- 지지: C의 사전 차단율이 A보다 높고 사람 이상, 오차단율이 낮음
- 기각: 차단율은 높아도 오차단이 많아 사람이 모두 다시 봐야 함
- 수치 기준은 시험 실행 후 사용자와 정한다

## 한계
- 사람 기준선은 1명이다
- 문서는 개발 중 쌓인 것이 아니라 나중에 쓴 것이다
- 소형 프로젝트 표본이 적어 규모 비교는 경향까지만 말한다
